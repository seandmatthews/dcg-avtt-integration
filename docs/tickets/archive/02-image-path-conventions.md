## Problem

Records carry an explicit `mapFilePath` (and optional `thumbnailPath`),
but where Atlas's *own* importer places images
(`src/app/services/vault-sync/assetImageFiles.ts` in the 0.6.0 tree) is
unchecked. README §12.2: match its convention unless there's a reason
not to — our published images should sit where the app expects its
own, so relinking, thumbnails, and library views behave.

## Proposal

Source-read task against a fresh clone at the pinned tag (AGENTS.md:
re-clone, never trust the README's memory of the source):

1. Read the importer's image placement + the record fields it writes.
2. Decide the vault-relative path convention our `scenes` publisher
   uses for the copied `<slug>.png` (README §5.1's plan shows
   `maps/<slug>.png`; confirm or correct).
3. Note whether thumbnails are generated by Atlas on adoption or must
   be supplied.

## Implementation notes (2026-10-10)

Source read against a fresh clone at the pinned tag **0.6.0**
(commit `c5a99830`, "Release 0.6.0 (#269)"; re-cloned per AGENTS.md to
`%TEMP%\atlas-vtt`). All file:line cites below are that tree.

**Correction to this ticket's premise.** `assetImageFiles.ts` lives at
`src/app/services/assetImageFiles.ts`, not under `vault-sync/` — and it
is the *UI drag-in importer's* helper, not the vault-adoption path. Its
`writeAssetImage` (lines 5–14) drops every imported image into the
shared folder `atlas-vtt/assets/` as
`<name, [^a-zA-Z0-9]→_>_<Date.now()>_<random36>.webp`: name-mangled,
timestamped, randomized, WebP-converted by the browser image workers.

**Decision — our publisher keeps README §5.1's `maps/<slug>.png`
(confirmed, not corrected).** The `scenes` publisher copies the site
image as-is to `atlas-vtt/collections/<collectionId>/maps/<slug>.png`
(PNG kept — no WebP conversion: stdlib-first, and a lossy transform is
not ours to make) and writes the record at `maps/<slug>.json` with
`mapFilePath` set to that vault-relative path. Reasons, all checkable in
the 0.6.0 tree:

- Adoption — the path our records actually take
  (`vault-sync/assetAdoption.ts`, `adoptMapJson`, lines 59–70) — reads
  `mapFilePath` out of the record and accepts any path that exists in
  the vault (checked against the full vault listing,
  `reconcileIndex.ts` `VaultListing.files`, lines 11–13). For adopted
  records, the stated path *is* the convention; the importer's
  `assets/…webp` habit is not one we must match.
- The `<timestamp>_<rand>` suffix exists to keep repeated UI imports
  unique and is incompatible with contract rule 3 (stable stems,
  refuse-on-diff). Atlas even carries a regex to strip that suffix back
  off when recovering names from `assets/` files
  (`recoveredIds.ts:recoveredTokenName`, lines 20–27).
- Sibling placement (`maps/<slug>.png` beside `maps/<slug>.json`) fits
  Atlas's own model: a map's *primary* file is its image and the record
  JSON is a sidecar that "follows the asset"
  (`vault-sync/assetFiles.ts` `primaryPath`/`sidecarPath`, lines 52–65
  and 83–86). Relink re-finds a moved file by exact base name among
  unowned files (`assetRelink.ts`, lines 27–44) — unique slugs keep
  that unambiguous, and app-minted ids (`<type>-<timestamp>-<rand>`,
  `AssetService.ts:963–965`) cannot collide with slugs.
- `id` stays omitted: adoption recovers it from the record stem
  (`stemOf` = basename minus extension, `recoveredIds.ts:18`) — the
  slug is the identity, as README §3.1 already states.

**Thumbnail answer: never supplied by us.** `adoptMapJson` ignores any
`thumbnailPath` in the record JSON — the adopted asset carries only
`mapFilePath` (lines 61–68) — so a thumbnail we wrote would be dropped
at adoption. `AssetThumbnailService` then background-generates
thumbnails for every map lacking one ("assets that lack one (older
assets, imported collections) get theirs generated in the background",
lines 47–55; `ensureThumbnails`, 167–174), writing
`atlas-vtt/assets/thumbnails/<name>-<8-hex digest>.webp` (256 px, q0.8;
`thumbnailPathFor`, 86–90) and recording the path back onto the asset.
Consequences: we never write into `atlas-vtt/assets/` at all — it is
Atlas's own folder — and `mapFilePath` is *required*: a map record whose
stated image is missing is skipped at the vault check
(`assetAdoption.ts:62`), so the publisher writes the image first, then
the record. (The UI importer generates its thumbnail at import time,
`import/uvtt/importUvttFile.ts:94`; that convenience does not apply to
adopted records and is not needed.)

**README changes.** §5.1's plan was right, so §5.1 is unchanged. §3.1
gained the verified facts above (image-must-exist, thumbnail answer,
`assets/` is Atlas's own) and §12.2 is marked answered. No other doc

**Deviations.** `records.map_record`'s stub signature dropped its
`thumbnail_path=` parameter (docstring + `tests/test_records.py` pin the
decision instead): the spike's answer is that thumbnails are never
supplied, and keeping the parameter would invite the mistake. The writer
bodies themselves stay stubs — they land with the scenes build
(ticket 05).

**Bycatch for ticket 05 (scene records).** `adoptSceneJson` reads the
scene path from a *top-level* `mapPath` in the JSON
(`assetAdoption.ts:77`), while importer-written scene records nest it as
`data.mapPath` (`importUvttFile.ts:116`) and so re-adopt only through
the sibling `<stem>.atlasmap` fallback (line 78). Our layout
(`scenes/<slug>.json` beside `scenes/<slug>.atlasmap`) works through
that fallback either way; ticket 05 should decide whether our scene
records also state a top-level `mapPath`.
